# Optional browser control

Workbench manages the official Microsoft `@playwright/mcp@0.0.85` server as a local MCP child. Five grouped tools invoke it directly, without a Codex/DSH turn. The adapter validates its allowlisted methods against the child's actual `tools/list`; tests check the installed input schemas and exercise a local page in real headless Edge. Edge must already be installed. No browser download, extension, CDP attachment, user-profile import or headed fallback is performed.

Enable host policy `enabled` and add `browser: {"enabled":true,"allowed_hosts":["YOUR-HOST"],"state_directory":"E:\\Workbench\\browser","profile_name":"personal"}`. Use a dedicated state directory. `profile_name` is optional: when present its `profile-personal` directory retains its own login/storage across sessions; otherwise the temporary profile is removed on close. The adapter never uses the user's normal Edge profile. The dedicated profile needs its own login; sharing an existing Edge login through the official extension would require a separately authorized future integration. Private state is excluded from host file read/write/export tools.

`browser_session` creates/closes a session; `browser_tabs` lists/creates/selects/closes its tabs; `browser_navigate` accepts HTTP(S) URLs. `browser_observe` provides a depth-limited snapshot, literal snapshot search or text wait. `browser_act` clicks an exact observed ref or fills/types text. Every tool takes a typed `request` object. Names are identical in v1/v2. There are at most 32 tabs, a 1 MiB backend message bound, a configurable 1–45 second call deadline and 4–64 KiB text output bound. Truncation is explicit. Observation text is untrusted, and successful delivery requires application-specific verification. Calls are serialized; failures are never automatically replayed. After an uncertain mutation, inspect a fresh snapshot or explicitly close the session. Cancellation closes the owned backend before another call can proceed.

Sessions and selected tabs belong to one MCP connection in one Bridge instance. A tunnel/client must route successive calls to that owner. Another Bridge cannot recover its in-memory session; it must create a new one. A persistent profile preserves storage, not tabs or pending actions. Its exclusive filesystem lock prevents simultaneous owners across Bridge processes. Normal disconnect closes the child and releases the lock; after an abrupt host crash, an administrator must verify the old processes have ended before removing a stale `.lock`. No automatic lock takeover or mutation recovery occurs. Different `profile_name` values create independent profiles.

Closing the connection removes temporary output and profiles, retaining only explicitly named persistent profiles. Persistent browser data has browser-managed disk growth and should be maintained locally. Navigation uses the current account's network access; this module is not a network sandbox. Live Bridge restart and client tool-metadata refresh are separate deployment steps.

Run the local-only acceptance test with `WORKBENCH_BROWSER_SMOKE=1 node --test dist/tests/unit/host/browser.test.js` after building. It tests both name profiles, real fill/type/click/wait and tabs, exclusive profile ownership, persisted test storage and disconnect cleanup; it uses no external site or authenticated data.
